### Tide

Tide is a design-first programming language project. `design/01-design.md`
is the decision record and owns every language decision; the chapters in
`design/` elaborate it and `design/reference.md` is the agent-loadable core
reference. `research/` holds cited evidence, `reviews/` the adversarial
reviews, and `trials/` the learnability experiments. `archive/v0-design/` holds
the superseded first design and its early Rust scaffold.

### Governance

`GOVERNANCE.md` binds every change:

- production code is agent-produced; mark any human-written production code as
  an explicit exception;
- no change lands on `main`, by PR or direct commit, without an AI
  supervisor verdict. The first review round runs two read-only reviews
  in parallel on one frozen candidate: an Opus review (a converge round,
  AP-PROOF-001, that reports instead of fixing, for code, tests, or
  scripts; a review round for docs-only design work) and one Codex pass
  (`gpt-6.1-sol`, always `xhigh`). Fix what both found once both are in,
  run Opus confirmation rounds until one comes clean, then a narrow Codex
  re-check of the changes since the candidate, unless there are none. If
  that leads to any change, run one narrow Opus round and another narrow
  re-check; text-only fixes restart this loop at most twice. These Codex
  passes replace converge's own Codex round. Planning-only changes skip
  the Codex pass;
- a finding blocks or restarts a round when its fix would change a tier
  the change edits or an earlier one (usually the v0 core); one whose fix
  would change only later-tier text the change does not edit goes as a
  comment on bead `fx-djp` instead (`GOVERNANCE.md`, Merge Rule);
- substantial language or toolchain additions pass the low-entropy design
  admission filter.

### Beads

`br` tracks open work. Follow `BR_WORKFLOW.md` for `T###` task mapping, the
`TASKS.md` archive, and which `.beads/` files to commit.

### Verification

Production code is the root Cargo workspace under `crates/`: the `tide-admit`
admission driver, built with the nightly that `rust-toolchain.toml` pins, with
`rustc-dev`. `cargo test --workspace` tests it, and `conformance/run.sh`
checks the conformance corpus with stable rustc and the driver; both exit 0
when they pass. `spikes/` holds throwaway feasibility prototypes and
`trials/` the trials' oracles, each run by its own scripts, which choose
their toolchain themselves. Design changes are checked by review rounds and
learnability trials (`design/01-design.md` D0).

### Decisions

The owner sets scope, priorities, and direction (AP-SCOPE-001): what a
change delivers. How to deliver a chosen outcome is the agent's to decide:
technical design decisions, budgets and thresholds, how to apply review and
governance rules, and which leftovers and in-scope fixes a pending change
includes; this grants no write that a canonical protocol withholds.
Loosening a check that a bead's Acceptance or GOVERNANCE.md requires stays
the owner's call (see Autonomous runs). For a technical choice, do not ask
the owner, offer a menu of options, or end with an offer such as "want me
to…?", even when a bead says "owner decision" or "stop and ask". When a
technical choice is unclear, take a web research pass, then decide, record
the decision and its reasons on the bead and in its owning document, and
report it.

### Autonomous runs

These rules apply when the owner does not attend the run: they asked for an
unattended run, or a session runner started it. They add to AP-SCOPE-001,
AP-PLAN-001, and AP-SESSION-001; AP-SESSION-001's budgets still apply.

- Before work, take the bead's done condition from its Acceptance as a
  runnable check or a named observation, and close the bead only when it
  passes. Never weaken it to close the bead; weakening what done means is
  the owner's scope call, while a technical correction that keeps or
  strengthens the check is the agent's (see Decisions).
- A plateau is not a stop. When progress stalls, change approach.
- A dead end ends the bead's attempt: the done condition still fails after
  at least two approaches that differ in mechanism, not reruns or tweaks
  of one, or the bead needs an owner scope call (a technical question is
  not one; see Decisions). Comment on the bead with what was tried and why
  each attempt failed, or with the scope choice and a recommended answer;
  run `br update <id> --status blocked`, adding `--add-label owner` when
  only the owner can unblock it; and end the run. Never wait for an answer.
